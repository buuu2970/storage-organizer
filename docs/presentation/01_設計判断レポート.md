## 1. 開発目的と学校課題

### 発表で話す内容
> 学校課題は「録画の容量がいっぱいだが、どれを削除すればいいかわからないので選んでほしい」です。
> 録画は1本が大きく、同じ録画のコピーや、失敗した録画が知らないうちにたまります。
> でも、どれを消してよいか自分で判断するのは大変です。
> RecSort AI は、PC の中の録画を調べて「整理を考えるとよい録画」を **理由付き** で示し、
> 本人が確認して選んだものだけを、安全に Windows のごみ箱へ移すアプリです。

## 5. 重要な設計判断

### 5-1. データベースを使わず JSON にした
**発表用の説明**
> データの保存にはデータベースを使わず、JSON という普通のテキストファイルを使っています。
> 開発の途中までは SQLite（ファイル型のデータベース）を使っていましたが、0d85a3d で JSON に切り替えました。
> 統合版ではデータベースを全面禁止にしています。

**事実**
- af51973 で SQLite（db.py）を導入しました **【確認済み】**
- 0d85a3d で store.py（JSON）に移行し、db.py を legacy_db.py に改名しました。同時に RELEASE_CHECKLIST に「データベース禁止（SQLite 依存なし）」と書かれています **【確認済み】**
- 統合版では、SQLite のコードと移行機能も削除しました（610fdbc）**【確認済み】**
- 「なぜデータベースが禁止なのか」の理由は、文書に書かれていません。指定・制約として書かれているだけです **【不明・要確認】**（授業の条件なのかどうかを本人に確認）

**JSON 方式の安全対策（統合版 store.py）【確認済み】**
| 対策 | 仕組み | 該当箇所 |
|---|---|---|
| 書き込み途中で落ちても壊れない | 一時ファイル（.tmp）に書く → fsync → 置き換え | `_write_tmp`・`_write_json` |
| 書き込み後の確認 | 書いた一時ファイルを読み直して内容を比較する | `_write_tmp` |
| バックアップ | 置き換える前に、前のファイルを .bak に残す | `_write_json` |
| 壊れたときの復旧 | 壊れたファイルを .broken-時刻 に退避し、.bak から復旧する | `_load_json` |
| 保護情報を復旧できないとき | 整理操作を止め、再起動しても止めたままにする | `PENDING_MARK`、`protection_ok` |
| 新しい形式のデータ | schema_version が新しければ変更しない | `Store._check_schema` |
| 不要な全件書き込みの回避 | 判断はまとめて1回で保存。確認日時は終了時にまとめて保存 | `set_decisions`・`_set_user_many`・`mark_viewed`・`flush_user_state` |
| 大量データ | 調査場所ごとに分けて保存（inventory/*.json.gz）。解析結果は追記型の analysis.jsonl | `save_inventory`・`update_video` |
| 二重起動 | ロックを取ってから読み書きする | `instance_lock.InstanceLock` |

**デメリット・限界**
- 検索や集計はプログラム側で全件をメモリに読んで行います。何万件にもなるとメモリと時間を使います **【推定】**
- 保護・判断はファイルのパスで記録しているため、ファイルを移動・名前変更すると引き継がれません **【確認済み】**（INTEGRATION_NOTES.md）

> そのため、まず重複や失敗録画のように、はっきりした根拠で選べる機能を完成させることにしました。

**事実**

- shuhei 側で AI を外した当時の理由は、文書にありません **【不明】**
- 関連する記述として、試作版の README に「類似度は数値の傾向が似ていることしか表しません」とあります（af51973）**【確認済み】**

### 5-3. 全ドライブの自動スキャン
**発表用の説明**
> 録画がどこに保存されているかは、人によって違います。
> そこで、フォルダを選ばなくても、内蔵ドライブ全体を自動で調べるようにしました。
> Windows やアプリの領域は除外しています。調査中も操作でき、一時停止やキャンセルもできます。

**仕組み【確認済み】**（autoscan.py）
- 調べる順番は、ビデオ・デスクトップ・ダウンロードなどのフォルダ（`known_folders`）が先で、そのあと内蔵ドライブ（`local_drives`、`build_locations`）です。
- 除外する場所
  - Windows・Program Files・ProgramData・AppData：Windows の既知フォルダ API で実際の場所を取得します（`system_folders`、統合版で追加）。
  - キャッシュ・一時フォルダ・開発用フォルダ、アプリのフォルダ（`looks_like_app_folder`）
- リンク・ジャンクションはたどりません。循環や二重集計を防ぐためです（scanner.is_link）。
- オンライン専用のファイルは中身を読みません。勝手にダウンロードさせないためです（scanner.is_cloud_only）。
- 外付け・ネットワークドライブは自動では調べません（設定で追加できます）。この理由は文書にありません **【不明】**。安全面と負荷を考えた判断と思われます **【推定】**。
- 全体の件数が分からないうちは、進み具合を％で表示しません（565ff66:README.md に理由の記載あり）。
- 変更のないファイルは、以前の解析結果を再利用します（analysis.jsonl を「パス・サイズ・更新日時」で照合）。

**負荷**

### 5-4. 重複検出（SHA-256）
**発表用の説明**
> 同じ録画のコピーは、ファイル名ではなく中身で判定しています。
> まずサイズが同じファイルだけに絞り、その中身全体から SHA-256 という「指紋」を計算して比べます。
> 指紋が同じなら中身も同じなので、1本だけ残して残りを整理候補にします。

**仕組み【確認済み】**（candidates.find_exact_duplicates、candidates.Context）
- 指紋（SHA-256）を計算するのは、サイズが同じファイルがあるものだけです。計算前後でファイルが変わっていたら、結果は使いません。
- ハードリンクや別の表記で同じファイルを指している場合は、重複として扱いません（`file_identity`）。
- 各グループで必ず1本を残します。残す1本は、保護 → お気に入り → 最も古いもの、の順で選びます。
- 移動の直前にも、残す側が実在して変更されていないかを再確認します（trash.survivors_check・_keeper_ok）。
- 「最も古いものを残す」理由は文書にありません **【不明】**

### 5-9. ごみ箱への移動と完全削除の防止
**発表用の説明**
> 削除は「完全削除」ではなく「Windows のごみ箱への移動」にしています。
> 間違えても、ごみ箱から元に戻せるようにするためです。
> さらに、Windows が「ごみ箱に入らないので完全に削除します」と判断した場合は、
> その瞬間に操作を中止する仕組みにしています。

**旧方式の問題点（統合時に発見）【確認済み】**
- shuhei 版は `SHFileOperationW` に `FOF_WANTNUKEWARNING` を指定していました。
- この組み合わせでは、ごみ箱の容量を超えた場合などに Windows が「完全に削除しますか？」と確認を出します。そこで利用者が「はい」を押すと、完全削除される経路が残っていました。

**新方式（610fdbc、recycle_bin.py）【確認済み】**
1. **事前確認（`precheck`）**：次のどれかに当てはまれば、移動しません。
   - 通常のファイルではない／リンクである
   - オンライン専用のファイルである
   - 固定ドライブではない
   - ごみ箱が使えない
   - 「ごみ箱に移動しない」設定になっている
   - ごみ箱の最大サイズを超える
2. **実行中の確認（`_on_pre_delete`）**：Windows の `IFileOperation` を pywin32 で使います。削除直前の通知（`PreDeleteItem`）に「ごみ箱へ移す」印（TSF_DELETE_RECYCLE_IF_POSSIBLE）がなければ、その場で中止します。
3. **実行後の確認（`decide_from_sink`）**：ごみ箱の中に項目ができたことを確認できたときだけ「成功」とします。
4. **失敗したとき**：別の削除方法には切り替えません（フェイルクローズ＝安全側で止める）。

**アプリ側の安全確認（shuhei の trash.py）【確認済み】**
- 移動するのは、利用者が明示的に操作したときだけです。
- 保護中は移動しません。
- スキャンした後にファイルが変わっていたら移動しません。
- 重複グループの最後の1本は移動しません。
- 類似録画は、残す1本を確定するまで移動しません。
- 結果は「移動した／止めた／失敗した」に分けて表示し、trash_log.jsonl に記録します。

**統合版で追加したこと【確認済み】**
- 移動は「削除候補」画面の最終確認と、確認ダイアログの承認の後にだけ行います（FinalPage.confirm）。
- 古い移動ダイアログ（TrashDialog）は削除しました。GUI スレッドで動き、一部の確認を通らない古い経路だったためです。

## 10. 重要な設計判断のまとめ（1枚で話す用）
1. **人が最後に決める**：アプリは理由付きの候補を出すだけ。移動するのは、最終確認で承認したものだけ。
2. **完全削除しない**：ごみ箱だけを使い、ごみ箱に入らないと分かったら中止する。
3. **根拠のあるルールで判定**：重複（SHA-256）・短い・黒画面・読み込み失敗・無音。容量が大きいだけでは削除をすすめない。
4. **データベースを使わない**：JSON で保存。一時ファイル・確認・バックアップ・復旧で壊れにくくする。
5. **課題に集中**：AI・画像整理・圧縮は後回し。元のコードはブランチに残してある。
6. **土台は安全修正が入った 7ac00eb**：0d85a3d には、保護データが壊れると保護なしで動く問題があった。
7. **画面はブラウザ、処理はそのまま**：ブラウザ版でも、安全確認を含む処理はデスクトップ版と同じコード。インターネットには公開せず、合言葉のない要求は断る。
8. **デモは分ける**：発表では `--demo` で合成の録画だけを使う。自分のファイルをスクリーンに映さず、本物の記録とも混ぜない。
